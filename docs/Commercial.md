# Shared catalog, quotations and receipts

The `/commercial` workspace records a reusable item and price catalog for the authenticated operator's store and issues A4 commercial documents. Save each item, price and photo once, then reuse it across every store and branch that operator can manage. For PLC management this includes authorized customer stores; each customer store retains its own separate catalog when its users sign in. The store and branch selectors choose the document destination and history, and do not switch catalog ownership. These documents do not create restaurant orders, change stock, or post to POS sales reports.

## Workflow

The main workspace presents three numbered, connected tabs: **Catalog → Quotations → Receipts**. All three remain directly accessible, retain the selected store/branch, and synchronize the chosen tab with the URL. These tabs organize the commercial workflow; document creation and editing use a complete form.

1. Search for an accessible store and branch in the two destination fields. Both accept Lao/English names and identifiers. Branch administrators are limited to their authenticated branch; other management access follows the existing live store classification and branch policy. Switching the document destination retains the shared catalog and synchronizes the list URL for refresh and browser navigation.
2. Management roles 1 and 2 can add or edit shared items, whole-LAK prices, units and optional JPEG/PNG/WebP images up to 5 MB. Item image visibility and active status are saved on the server. Branch administrators can read the catalog and use its items in their own branch's documents, but cannot change the shared items. The PLC examples prefill a form and never silently create records.
3. Follow the quotation or receipt creation link to its own editor page inside the normal application shell. Document dates/payment, customer, issuer, items/photos, private payment details and discount/VAT/notes are visible together in one scrollable form. Desktop shows the form on the left and its live A4 document preview on the right, with separate scrolling. Mobile provides Details and Preview tabs that retain the same form, edits and preview. Customer/issuer details, items, prices, images, dates, notes and VAT update the preview immediately. VAT starts at zero; the ten-percent option is an explicit document setting.
4. Leave the optional footer discount blank or zero to omit it from the preview, issued document and PDF. Enter a whole-LAK amount or a percentage with up to two decimal places to deduct it before VAT. The discount cannot exceed the subtotal.
5. Save before printing or downloading. Issued documents retain their own names, prices, images and totals even after catalog edits. Follow **Edit document** from history or the saved preview to fetch the latest version on its editor page. Existing lines retain their original text, prices and photos even if their catalog item has since changed or become inactive. Saving keeps the document UUID/number, records a new revision and returns to the chosen history tab with a fresh saved-document preview.
6. Use **Revision history** to view earlier saved snapshots read-only. A version conflict leaves the editing draft intact: review the latest saved version, or explicitly confirm replacing the draft with it. Linked documents are edited separately; editing a quotation does not change an already-linked receipt.
7. After payment has been received, use **Issue receipt** on its quotation and confirm the date and payment method. Conversion checks the displayed quotation version before issuing a new receipt, and pins the source quotation number/version. Repeated conversion returns the same linked receipt.

Creation requests use a stable `request_uuid` for each attempted document. After an ambiguous creation failure the form locks its attempted content while retry recovers that exact document; further corrections can be made after recovery. Update retries reuse one request UUID for identical content. Changing content after a failed update creates a new operation while retaining the originally loaded expected version, so a committed earlier attempt produces a visible conflict rather than discarding new edits. All replays still require current authentication, menu permission and branch access.

The live preview uses the same document renderer, selected system font and photo/logo rules as issued documents. New documents display a draft marker instead of an issued number; editing an issued document keeps its number and shows an unsaved-changes badge. Typing does not save anything or offer draft printing/PDF export. The same draft, mounted fields and preview remain in place through mobile Details/Preview tab changes. Enter in a document input does not issue the document; Enter in a textarea keeps its normal newline behavior. The fixed Save button validates the entire form before recording an immutable version snapshot. Invalid data reveals Details and focuses the first affected field or payment selection, including when saving from the mobile Preview tab. Retry recovery and conflict checks remain explicit Save actions.

## Private payment accounts and QR

The inline payment section above notes and totals can save and edit reusable bank profiles: label, bank name, account holder, account number, LAK/THB/USD currency and an optional PNG/JPEG/WebP QR upload up to 5 MB. Up to 20 profiles belong only to the authenticated user in their authenticated store. Choosing a customer store or document branch does not change that owner. All three commercial roles can manage their own profiles; users in the same store cannot list or edit one another's private profiles. No deletion is offered; removing a profile's QR requires confirmation and saves that edit separately from any document.

New quotations and receipts start with **Show account numbers** and **Show payment QR** off. Choose up to three profiles and explicitly enable the footer fields to include. Turning a switch off retains the editor's selection, while both switches off sends no account references. The shared document and its revisions retain only opted-in numbers and QR assets. Saving a private profile does not issue or revise a document. Existing document bank snapshots remain unchanged until the user explicitly chooses **Use latest saved account details**, which selects their current private profile for a new snapshot. A number or QR omitted from an earlier snapshot cannot be recovered by toggling visibility; select current private details again. Legacy issued bank text keeps its prior visible behavior, while new issuer bank text requires the account-number switch.

Document and revision lists omit QR image bytes and carry `has_qr` metadata. Full document reads and `/documents/:uuid/revisions/:version` hydrate the exact visible saved QR before editing, previewing or printing. Same-version list responses preserve already hydrated QR data; a newer summary requires a fresh full read and never reuses an older version's QR. Native PDF output retains raster QR images losslessly and uses a neutral gray table header.

Private profiles use Backend persistence only. They are not written to localStorage, public assets or repository fixtures. Their in-memory cache clears immediately on user, authenticated-store or token changes, and late loads/saves cannot repopulate another session. Synthetic test account numbers and QR images are used for automated verification.

Creation uses `/commercial/new?type=quotation|receipt&store_uuid=...&branch_uuid=...`; edits use `/commercial/<document_uuid>/edit?store_uuid=...&branch_uuid=...`. These are real links that support direct entry and refresh. Back links return to `/commercial` with the selected scope and `tab=quotations|receipts`; a saved `document_uuid` in that history URL reopens the saved output after an authenticated read. Both editor pages verify the base commercial menu permission and resolve their requested scope before loading data. An inaccessible requested write destination displays an error rather than silently choosing another branch. Transient route leases invalidate old details, overlays, errors and pending editor results without resetting a newer page's verified scope.

Catalog responses carry `catalog_store_uuid`, which must match the authenticated store. The retained item `branch_uuid` records its creation provenance; it does not restrict reuse or image access to that branch. The request's selected `branch_uuid` remains an authorized context, while the server derives catalog ownership from the live authenticated actor. Neither the selected customer store nor a client-supplied owner can change it. A wrong-owner response rejects the entire result and clears cached catalog data. Logout or owner changes also invalidate pending catalog work. Document reads, writes and saved snapshots remain strictly scoped to their target branch.

## Deployment

Deploy the companion Backend changes first. Its existing deployment workflow now runs:

```sh
npm run migrate:commercial-documents
```

The runner applies `20261114_add_commercial_documents.sql`, `20261114_share_commercial_catalog_by_store.sql`, `20261114_add_commercial_document_revisions.sql`, `20261114_add_private_commercial_payments.sql` and `20261114_add_commercial_menu.sql`. All are rerunnable; existing issued snapshots and explicit permission denials are preserved. The catalog migration backfills authenticated-store ownership for existing items without moving their original branch or photo. The revisions migration retains the initial issued version while adding edit history, stable line identities and optional discount values. The private-payments migration adds user-owned reusable profiles and opt-in document payment snapshots while retaining legacy bank-text visibility for previously issued versions. The menu migration follows each installation's existing Branches settings group and grants access only to eligible management scopes. A missing schema produces a visible `COMMERCIAL_MIGRATION_REQUIRED` error instead of a local success.

The API lives under `/api/v1/commercial` and uses the existing object-storage configuration. No new dependency, Next server business logic, offline database, or runtime secret is required. The default issuer logo is the bundled `/brand/plc-logo.png`; the issuer fields remain editable.

## Output

The preview, browser printing, price lists and PDF downloads share the isolated Lao document renderer. They follow the current Appearance → Lao font selection and use the same bundled font files, glyph coverage, weight registrations and Phetsarath Latin fallback as the app. The selected face supplies its own Lao, Latin and digit glyphs where available. The print-only stylesheet keeps these A4 documents independent of the legacy receipt font rules. PDF export also loads the separate font-face-only stylesheet into the application's document, where html2canvas creates its drawing canvases, without changing application typography. It validates the chosen Lao face and Latin font separately at regular and bold weights in both documents before drawing; an available fallback cannot conceal a missing chosen font.

Printing waits for fonts and requested images. PDF export pins the resolved font family and also loads/validates the faces inside html2canvas's cloned document before it reads styles. That clone has a separate font set, and its early `fonts.ready` can resolve before cloned external stylesheets or imports load. A missing selection rule must never silently turn the output into Times. PDF export measures complete rows, repeats headings, and keeps the final totals/signatures together. An unavailable requested image/font or an oversized row produces an error rather than a silently incomplete file. Users can explicitly hide images and export again. Font regression QA must trigger the real parent-page download button: executing the exporter inside its preview iframe hides cross-document font failures. Compare system/preview/canvas glyph metrics for all four Lao choices, including Latin, digits and bold, then render and inspect the downloaded PDF itself.

The A4 layout retains the original centered bilingual heading, issuer information with document number/date on the right, and customer information below the issuer. Gray column headings are 14px; the grand-total label/value are 16px with a 12px currency label. Very long grand totals use a 14px value to retain every digit, and unusually long quantities receive a wider column. Downloads capture lossless PNG pages at 300 dpi, preserving the selected font's shaping and QR modules.

Live preview, saved preview, native printing and PDF use the same row-based A4 page layout. Natural rows are distributed before an empty, accessibility-hidden table row fills the remaining printable height. This extends the column rules and anchors the final totals/payment/signature/footer block at the bottom without stretching item rows or overlapping private QR images. Each page repeats the header; final details appear only on the last page. Preview retains one offscreen canonical source, regenerates pages atomically after fonts/images load, and discards stale async results. Oversized content produces a visible error and can recover after editing. Check actual PDF/native-print page counts, row order, footer positions, numeric cell boundaries and narrow-screen exports when changing these dimensions.

Verification covers shared-catalog reuse and original images across target stores/branches, owner isolation, management-only catalog changes, document branch isolation and late/lost responses. Payment checks cover same-store user isolation, authenticated-store/token cleanup, late profile responses, explicit field omission, immutable retained snapshots, exact-version revision hydration and list/full-read races. Browser QA also covers mobile/desktop widths, Lao dark mode, uploaded-image persistence, quotations, linked receipts, image-load failures and multiple A4 pages. Physical printer output and native APK download handling require separate device acceptance.
